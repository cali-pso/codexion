# Codexion

## Description

This is my shot at the codexion project from 42's curriculum. It aims
for a better understanding of multithreading, mutexes and condition variables
in C through a variant of the Dining Philosophers' Problem. This implies handling
blocking cases and implementing synchronisation between threads, subjects to be
discussed later on.

A Makefile has been provided. Run:

## Blocking cases handled

Coffman's condition is avoided thanks to the **resource hierarchy** solution,
negating circular wait. Each coder tries to get it's dongles in the same order:
first the right dongle (lowest id), then the left (highest id). That is true for
every one of them except the last one : sharing a dongle with coder 1, it's left 
dongle is the lowest id. So the last coder locks left first, then right. This way,
if every coder locks it's first-wanted dongle, the last coder is blocked from
locking anything, and coder last - 1 can compile, preventing the deadlock.

A known problem of this solution is it's **unfairness**: unfortunate timing can lead
to a recently satisfied coder picking up a dongle in place of a soon-to-burnout
coder, leading the simulation to failure. This has been prevented by delaying
the creation of each coder thread by a millisecond.

## Thread synchronization mechanisms

The use of mulithreading forces mechanisms to protect memory from race conditions,
where two threads attemps to read/write a point in memory simultenaously, resulting
in a different state each execution from the order in which those threads access 
the memory. To fix this I use a big **system** data structure that holds every other
necessary structure, like coders or dongles, or output. Each of these structures
has a mutex lock to allow anyone who reads/write to it to do it safely. Dongles
also have a condition variable used to wake up coders waiting on them.
